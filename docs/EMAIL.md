# Invitation email

Creating a DSP queues an email to its owner. The email includes a **Start DSP
onboarding** button. Accepting the invitation signs the recipient in and opens the
invited DSP's setup form. Team invitations use **Accept invitation**. The API and
dashboard never return the invitation URL to the sender.

## Environment isolation

Dev and Production run separate platform databases, keys, outboxes and DSP state.
An invitation belongs to one database and environment. Its URL uses that
installation's canonical `DISPATCH_ORIGIN`. Dev emails carry `[Dispatch Dev]` in
the subject and use a separate Cloudflare Worker, sending subdomain and secret.

The backend selects **only** the matching configuration prefix:

| Installation              | Prefix                 | Origin                                |
| ------------------------- | ---------------------- | ------------------------------------- |
| Dev (`preview`)           | `DISPATCH_DEV_`        | `https://dispatchdev.dillonlille.com` |
| Production (`production`) | `DISPATCH_PRODUCTION_` | Production's canonical origin         |

Each prefix supports `MAIL_MODE` (`cloudflare`, `smtp`, `disabled`, or local-only
`capture`), `MAIL_WORKER_URL` and `MAIL_WORKER_TOKEN`. SMTP additionally uses
`SMTP_URL` and `MAIL_FROM`. There is no fallback to the other environment's
configuration or to the retired unscoped mail variables.

Hosted installations default to `disabled` until configured. Email invitation
requests fail before provisioning if mail is disabled. Local fixtures explicitly
use `capture`; messages are private files under `data/platform/development-mail/`.
Capture is refused with `NODE_ENV=production`, including hosted Dev.

## Cloudflare Dev setup

The committed Worker configuration at `services/cloudflare-mail/wrangler.jsonc`
is Dev only. It sends from `invitations@dispatchdev.dillonlille.com`, accepts only
`preview` messages for the Dev origin, and requires a private `MAIL_TOKEN` secret.
The email binding restricts the sender. No Cloudflare API credential is stored in
the application.

1. Onboard `dispatchdev.dillonlille.com` under Cloudflare Email Service > Email
   Sending. Keep message previews disabled because invitation messages contain
   private account tokens.
2. Validate the Worker with
   `npx wrangler@4.133.0 deploy --dry-run --config services/cloudflare-mail/wrangler.jsonc`.
3. Generate a random `MAIL_TOKEN` of at least 32 characters in a private JSON
   secrets file outside Git. Deploy with the same command without `--dry-run`,
   adding `--secrets-file /absolute/private/secrets.json`. For later secret changes,
   use `wrangler secret put MAIL_TOKEN --config services/cloudflare-mail/wrangler.jsonc`.
4. Store the following in Dev's private `config/platform.env` (mode 0600), using
   the deployed URL and the same secret. Restart Dev after its updated build is
   installed.

```text
DISPATCH_DEV_MAIL_MODE="cloudflare"
DISPATCH_DEV_MAIL_WORKER_URL="https://<dev-worker>.workers.dev/send"
DISPATCH_DEV_MAIL_WORKER_TOKEN="<private-dev-secret>"
```

The worker types are generated by `node tooling/mail-types.mjs`. Its module wrapper
keeps Cloudflare globals separate from dashboard and Node types.

## Production release setup

Production uses the same tested application flow with its own configuration.
Create a separate Worker configuration and deployment with a different name,
`DISPATCH_ENVIRONMENT=production`, the Production origin, a Production-only
sender/binding and a new `MAIL_TOKEN`. Set only `DISPATCH_PRODUCTION_MAIL_*` in
Production's private configuration. Do not copy Dev's config, secret, database or
outbox. Publishing application code does not provision the Dev Worker for
Production or deploy any Worker automatically.

## Delivery and verification

Messages enter the installation's encrypted outbox and are delivered in the
background. The dashboard says the email is queued; it does not claim inbox
delivery. Cloudflare failures retain encrypted messages for exponential-backoff
retries (five attempts). Successful acceptance clears their encrypted contents.
Worker logs contain delivery failure events without addresses or message bodies.
The operator can inspect outbox `status`, `attempts` and `sent_at`, and Cloudflare
Email Service activity, without exposing invitation tokens.

Tests cover the captured HTML button through account creation and DSP onboarding,
existing accounts, revocation, expiry, Dev/Production isolation, disabled mail,
Worker authentication and outbox retry/acceptance. Local and CI tests do not send
external email. Verify real delivery with an explicitly chosen test recipient.
